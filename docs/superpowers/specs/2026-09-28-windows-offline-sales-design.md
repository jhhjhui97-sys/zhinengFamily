# Windows offline customer and project workflow

The user wants a usable Windows-local sales and design app at minimal cost. The existing portable Edge client already creates and versions scenes in local SQLite and renders four realistic **demo** models without a network connection. This step adds the missing customer → project → scene navigation. It does not turn those demo models into sellable products, add a catalog import, or claim the full quotation/CAD/AI workflow is finished.

## Approach

Keep the single loopback Node server, C# bridge, and `LocalSceneStore` as the only write path to `scenes.sqlite`. Reusing the FastAPI admin UI would introduce a server, login, and PostgreSQL dependency and would break the user's offline requirement. A second local database would risk split transactions between projects and scene links. Add a v2 schema to the existing SQLite database, with the same local workspace ID used by scenes.

The migration is additive. For an existing v1 database, create a SQLite online backup in the same user-data directory before starting the migration transaction; never overwrite a prior backup. Add customers, projects, and project-to-scene links, then set `PRAGMA user_version=2` in one transaction. A failed backup or migration aborts startup without modifying existing scenes or versions. The pre-v2 backup is the rollback path: close the app and restore that backup over `scenes.sqlite` after copying the current v2 database aside. Fresh databases create all tables at v2. v2 reopens without repeating a backup. `LocalIdentity` accepts v2 and checks the workspace IDs in the new tables.

`local_customers` stores generated UUID, workspace ID, name, phone, WeChat, source, address, optional decimal **string** budget, `new/following/won/lost` status, notes, timestamps, and an integer edit revision. A nonempty phone is unique per workspace; identical names are allowed because real customers can share names. `local_projects` stores generated UUID, workspace ID, immutable customer ID, name, address, `draft/active/archived` status, local actor as sales provenance, timestamps, and an integer edit revision. Project names are unique **within a customer**, and may repeat for different customers. All reads and writes include the locally generated workspace ID; callers cannot provide workspace/actor IDs. This is single-user local provenance, not remote authentication. Customer and project edits require the last observed edit revision; a stale edit returns 409 and preserves the form.

`project_scenes` associates an existing `scene_documents` row with a project using composite workspace foreign keys. A project may have multiple design scenes. Creating a project scene inserts the scene and link in one SQLite transaction. Every current/save/restore/version operation on a linked scene checks its project association; omission or mismatch gives 404. Existing v1 scenes remain **unlinked**, unchanged and available under a clearly labeled “旧方案” view. No fake customer is fabricated during migration. Unlinked legacy scenes retain the former API flow; a linked scene cannot be accessed through it.

The browser continues to use POST `/api/local` with same-origin and the existing HttpOnly SameSite loopback cookie. New bridge actions expose customer and project list/create/edit, project-scoped scene list/create, and legacy list. Responses are JSON without SQLite internals. Existing `scene.schema.json` validation and immutable scene version semantics remain unchanged. The fixed bundled model IDs stay marked `offline_catalog_only`; a future sellable catalog must have separate stable product identifiers and an explicit local model mapping.

## User flow

The left panel shows customers, customer projects, and each project's scenes. A salesperson can add or edit a customer, open that customer, add or edit a project, create a design scene within it, load the existing two-bedroom template, place a demo model, save v1/v2, restore an earlier version, and reopen after app restart. An “旧方案” section opens prior scenes without pretending they belong to a customer. Selecting another customer/project/scene or closing the window warns about unapplied or unsaved scene and form edits. Loading, duplicate submission, validation, 404, 409, and local-service failures have Chinese feedback. At iPad landscape width the three-column layout must avoid horizontal overflow, though this delivery targets Windows.

## Verification

Tests use real SQLite and independent store instances for migration, backup, rollback, cross-workspace isolation, duplicate names/phones, cross-customer scene association, stale edits, immutable history, and v1 reopen. Real Edge browser tests cover customer → project → scene → save/restore → service restart, including form preservation on conflict. The fully packaged app and normal visible-window launch are retested without remote requests. Existing 3D model rendering and all previous scene tests remain green. The exact pushed commit must pass Windows Local, Scene consumer core, and backend Actions before the new draft PR is considered reviewable.
