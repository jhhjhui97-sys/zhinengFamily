# Windows local client: runtime acceptance design

The user delegates technical decisions and continuous development. Windows local use and convincing furniture rendering are the delivery requirements; iPad packaging is deferred. Existing offline SceneModel and immutable version storage remain intact.

Reuse Unity 6000.3.0f1 and the existing isolated checkout. First establish real Editor import, existing seven Editor tests, Play, Windows x64 Player build and launch. Console tests and GitHub CI are separate evidence and cannot certify engine compilation. Only after this gate, plan realistic geometry, licensed PBR materials, lighting, shadows and actual application screenshots.

Install official signed tooling on D: because C: has only approximately 10 GB free. Do not purchase assets/services or bypass license checks. Unity account sign-in and confirmation of an eligible license belong to the user; credentials must never enter commands or logs. Downloads and generated engine/build caches stay out of Git. Preserve earlier branches and PRs; no merges.

A working Windows executable must operate without a backend or internet for bundled scenes and local save/restore. Use existing SceneModel coordinate and identity contracts. Realism will be judged from actual runtime frames, not generated concept images. This first bounded implementation stage proves engine readiness; it does not declare the whole app finished.

Acceptance: actual Editor test XML, build result, Windows launch evidence, local v1/v2/restore persistence. If licensing blocks execution, record that exact boundary without declaring tests passed.
